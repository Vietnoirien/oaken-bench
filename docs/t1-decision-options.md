# T1 decision options for the maintainer

Status: proposal, 2026-09-27. The [maintainer decision on #45](https://github.com/Vietnoirien/oaken-bench/issues/45#issuecomment-5831317870) defers T1. The `ready-for-agent` label on [#46](https://github.com/Vietnoirien/oaken-bench/issues/46) does not override its explicit instruction to wait for a changed decision. This note does not authorize implementation.

## What the evidence says

T1 was proposed to locate the roughly 75% Gemma T2 plateau by supplying the rest of the reference engine and asking the model to implement one module. [#26](https://github.com/Vietnoirien/oaken-bench/issues/26) estimated about five minutes per module and made T1 conditional on per-test T2 data being too coarse. [#46](https://github.com/Vietnoirien/oaken-bench/issues/46) proposes direct, pi and dsh modes; a restored reference module must score 100% before a package can be used.

The re-score in [#45](https://github.com/Vietnoirien/oaken-bench/issues/45#issuecomment-5811048952) could not recover the three original 192k Gemma workspaces that produced 23/132, 98/132 and 110/132. The two surviving 131k Gemma workspaces scored 27/132 and 58/132; their module results disagreed. Economy and run were 0/12 in both, but combat moved from 0/35 to 22/35 and snapshot from 18/24 to 0/24. That is too little evidence to call either module a fixed model weakness.

The later three 5070-only 192k DSH runs have archived workspaces. They scored 16/132, 36/132 and 41/132; one declared done with tests red and two crashed after 270-330 seconds. Economy moved 9/12, 0/12, 1/12 while items moved 0/15, 15/15, 13/15. Only seven test digests passed in all three runs. [MODELS.md](../MODELS.md#192k-with-less-free-5070-memory-2026-09-25) records the serving setup and results; [#45's update](https://github.com/Vietnoirien/oaken-bench/issues/45#issuecomment-5833463896) keeps the defer decision. These are early exits, not replications of the original plateau.

The current other-project demand is short tool chains, recall at context depth and abstention, according to [#26's scope comment](https://github.com/Vietnoirien/oaken-bench/issues/26#issuecomment-5809842173). T1 measures code implementation and therefore has a lower near-term payoff. Harness comparison is also a minor concern until more harnesses join the study, per the maintainer's current direction.

## Choices

| Choice | What it would answer | Work and GPU cost | Decision rule |
|---|---|---|---|
| Keep deferred (recommended now) | Let T0/T0.5 repetitions and T2 workspaces establish whether another coding probe is useful. It produces no new T1 score. | No T1 build or GPU time. Preserve the archived Gemma workspaces. | Revisit when comparable Gemma T2 runs finish normally or reach the clock cap, with archived workspaces and per-file counts. Look for the same weak module across at least three such runs after accounting for files the agent actually edited. |
| Drop T1 from the planned ladder | Accept that T2 per-file detail and run traces are the coding diagnostic this project will fund. | No further T1 cost. Remove or close #46 only after recording the choice on #45 or its successor. | Choose this if the project stays focused on tool chains, recall and abstention, or if T2 per-file patterns become clear enough to answer the coding question. The present early exits alone do not justify claiming T1 is unnecessary. |
| Minimal direct diagnostic | Test whether one or two prespecified modules can be implemented when the rest is supplied. It separates module implementation from T2 task-order and time-allocation failures. It does not estimate a harness effect. | Package and validate one or two modules, then run at least three independent direct trials per module: 3-6 trials. At #26's unvalidated five-minute estimate, roughly 15-30 minutes of inference, plus package/oracle work and scoring. | Pick modules before looking at pilot outputs; economy and items give a useful contrast because their recent T2 results moved in opposite directions. Expand only if the restored-reference control is 100%, the direct trials engage with the module and their pass pattern repeats. If results still track random early stops or package ambiguity, stop. |
| Full T1 study | Estimate module-by-module implementation outcomes and, if still wanted, direct/pi/dsh differences under matched conditions. | Eight modules times three independent trials is 24 trials per mode. At the five-minute estimate this is about two GPU-hours per mode, or six GPU-hours for all three, before package construction and scoring. Longer trials and retries can raise this substantially; set a per-trial cap before running. | Fund this only if module-level coding is a primary research question, the minimal diagnostic shows a repeatable gap, and several harnesses are available for a useful comparison. Report each module and mode separately, with spread and outcomes, never as one ladder score. |

The time arithmetic uses [#26's](https://github.com/Vietnoirien/oaken-bench/issues/26) estimate, not a measured T1 runtime. The recent Gemma T2 early exits took 4.5-5.5 minutes, but those are different tasks and do not validate the estimate. Specify a cap and a maximum GPU allocation before authorizing either build path.

For the minimal diagnostic, interpret the result before adding modes. If direct trials repeatedly pass a module that T2 omits, investigate T2 work order, task planning or clock use. If direct trials repeatedly fail it despite a passing reference control, the isolated implementation task has found a candidate model limitation. If direct results swing as widely as T2, more module packages will not fix the variance. A failing reference control invalidates the package. None of these patterns can establish a harness effect from direct runs alone.

## Conditions before any T1 pilot

1. Preserve the existing T2 instrument. Do not edit `seed/SPEC.md`, `seed/data/items.json` or files in `FROZEN.sha256`; give T1 its own results namespace and score. Do not backfill old runs.
2. Keep the reference engine and task packages sealed at rest. Restoring the reference module must pass all 132 v1.0 held-out tests and typecheck cleanly before any model trial. A per-module denominator also needs a documented mapping from held-out files or digests to the target module; cross-module tests may make a naive file-only score misleading.
3. Keep oracle source, test names and reference code out of published artefacts and model-training surfaces. Publish counts and digests only. Check the relevant canary before scoring, and record suite revision and model/server configuration. [CANARY.md](../CANARY.md) records that the reference-engine author has seen held-out failures and cannot author T1 specs or oracles.
4. Decide whether a hosted direct API is permitted to receive the seven supplied reference modules. Sending those modules outside the local machine changes the exposure of the sealed T2 solution. For a first pilot, local direct mode avoids that distribution problem.
5. Prespecify which model, module, trial count, stopping rule and success metric answer the decision. Keep completion/crash/timeout separate from test pass rate. Otherwise an early stop looks like module difficulty again.

My recommendation is to keep T1 deferred while new T0/T0.5 measurements run. If coding diagnosis later matters, authorize the minimal local direct diagnostic first. A full three-mode T1 study spends most of its budget on a harness comparison the project does not currently prioritize.
